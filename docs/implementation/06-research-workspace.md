## الخلاصة الصريحة

تم تنفيذ **شريحة تشغيل محلية متكاملة وقابلة للاختبار**، وليست كل خريطة الطريق متعددة الأشهر الواردة في البحث. البداية أصبحت مساحة عمل عربية بسيطة بدل تحويل الصفحة الرئيسية إلى مختبر تقني. تحت الواجهة توجد حالة محفوظة في SQLite وموافقات مرتبطة بالإجراء وتنفيذ قابل للاستئناف والتحقق من النتيجة.

المهارة التنفيذية المتاحة: **إنشاء مسودة فاتورة في ERP محاكى فقط**. لا نموذج لغوي متصل، ولا دفع، ولا OAuth لتطبيقات خارجية، ولا Odoo حي. واجهة الطلب تستخدم تصنيفًا محليًا بالكلمات المفتاحية لفتح المسار المناسب؛ لا تدّعي فهمًا عامًا أو استخراجًا ذكيًا للمستندات. التقارير تحسب البيانات الموجودة، ولا تختلق مقاييس أو وفورات.

## 2. إصلاحات الموثوقية التي كشفها الفحص

### أ. فشل reconciliation لم يكن غيابًا مثبتًا

كان `tryReconcile()` يعيد `null` عند غياب سجل **وعند فشل اتصال البحث**. مسار الأخطاء كان يستطيع إعادة المحاولة بعد فشل الاستعلام رغم احتمال حدوث الكتابة بالفعل.

أصبح الفصل ثلاثيًا:

- `found`: استخدام معرف السجل الموجود ثم التحقق منه.
- `absent`: رد ناجح صريح بلا سجل؛ يمكن إعادة المحاولة ضمن الميزانية في سياق الموصل التجريبي المتسق.
- `unknown`: خطأ أو رد غير ناجح أو بيانات غير مكتملة أو موصل بلا مصالحة؛ يتوقف المسار للمراجعة بدل التخمين.

**مهم:** حتى `absent` ليس كافيًا في أي API خارجي ذي اتساق احتمالي أو كتابة ما زالت جارية. لا تفعّل هذا المسار على موصل إنتاجي قبل توثيق ضمانات اتساقه ومفتاحه الفريد.

### ب. التحقق كان يقبل بعض البيانات الغائبة

كان غياب الإجمالي أو مصفوفة البنود قد يتجاوز فحص المطابقة. أصبح غيابهما، أو تغيير بند بنفس الإجمالي، أو تغيير الحالة إلى posted أو تغيير معرف السجل، سببًا لنتيجة `partially_succeeded`، لا نجاحًا وهميًا ولا إعادة كتابة عمياء.

### ج. الحالة غير المكتملة لا تعني نجاحًا

توقف العملية أثناء تهيئة الخطوات قد يترك مهمة بلا خمس خطوات كاملة. تم منع مسار النجاح الافتراضي في هذه الحالة: تتحول إلى مراجعة بفشل واضح. لم ندّعِ أن التهيئة متعددة السجلات أصبحت معاملة ذرية؛ هذا gap معلن وآمن الفشل.

### د. اكتمال دليل الموافقة

أصبح وجود approval ID مرتبط بالمهمة شرطًا إلزاميًا عند الكتابة؛ حذف المرجع لا يتجاوز الموافقة. تُراجع نافذة صلاحية الموافقة حتى لو حُسمت قبل انتهائها وتأخر التنفيذ. الإيصال يحتفظ بالسجل الكامل للقرار والمعلمات والبصمة بعد الاكتمال، وليس الطلب المعلق فقط.

### هـ. الاستئناف المتزامن

أضيف تسلسل لكل مهمة في الـ runtime، وليس فقط تعطيل زر المتصفح. اختبرنا ٨ طلبات استئناف متزامنة: موافقة واحدة ونداء كتابة واحد. قرار الموافقة نفسه يقبل حسمًا واحدًا باستخدام معاملة SQLite، بما في ذلك اتصالين بقاعدة البيانات.

## 3. قرارات المنتج

1. **الصفحة الرئيسية مساحة عمل وليست landing page أو مختبر أعطال.** محفوظة الواجهة القديمة في `/console` والمختبر في `/demo/invoice`.
2. **الأرقام الفعلية فقط.** عدد المهام والموافقات والنتائج محسوب من آخر ١٠٠ مهمة معروضة، وليس عدّادات seed.
3. **التدرج بدل الزحمة.** الطلب → مراجعة البيانات → خطة ثابتة معلنة → موافقة → نتيجة ودليل.
4. **لا ادعاء تكاملات.** ERP Sandbox مذكور كمحاكاة. Odoo وGoogle Workspace وMicrosoft 365 مذكورة كغير متصلة بهذه المساحة. اتصالات أدوات المحادثة خارج التطبيق لا تمنح التطبيق OAuth تلقائيًا.
5. **رفع نص محدود.** TXT/JSON حتى 8 KiB، قراءة محلية للنص دون OCR أو استخراج حقول تلقائي. البيانات المالية تُراجع في النموذج.
6. **لا أسرار في العرض.** لا توجد خانة مفاتيح API وهمية أو حفظ credentials في localStorage.

## 4. قراءة نقدية للبحث، لا تطبيق أعمى له

- المصدر يقدم توصيات هندسية مفيدة، لكنه ليس إثباتًا لأسعار السوق أو تفوق WAKIL أو جدواه التجارية.
- أسماء النماذج وأسعارها وتقييمات المنافسين المذكورة فيه لم تُتحقق عبر مصادرها الرسمية هنا؛ لا نعتمدها في البرمجة أو التسويق أو تقدير التكلفة.
- هناك خطأ تحويل وحدات في قسم الاقتصاديات: `$0.00791` يساوي **0.791 سنت**، و`$0.06374` يساوي **6.374 سنت**، لا 7.9 و63.7 سنت كما يوحي النص.
- تكلفة input tokens وحدها ليست تكلفة الاستدلال الإجمالية: يلزم output، retries، caching الفعلي، الأدوات، البنية، الإشراف والتصحيح البشري.
- نسبة هامش الربح لا تُحسب بدون سعر بيع مقاس، وتكلفة دعم واكتساب عملاء وتكاليف ثابتة موزعة.
- أحجام 1k/10k/100k مهمة يوميًا مذكورة كطموح؛ لم نجرِ اختبار حمل ولا نزعم أن SQLite/عملية واحدة يحققها.
- صفر أخطاء في fixtures لا يعني احتمال خطأ إنتاجي يساوي صفرًا. لا ادعاء امتثال تلقائي لـ EU AI Act أو أي تصنيف قانوني شامل.
- اختيار الفاتورة هنا **فرضية هندسية تستثمر الموجود**، وليس برهانًا أنها أفضل سوق. لو لم يكن Odoo موجودًا، قد يكون document operations أقل تكلفة تكامل؛ ذلك يحتاج مقابلات وتجارب مقارنة.

## 5. خطة إثبات الجدارة التالية

### تجربة بشرية وسوقية

- تجنيد 5–10 فرق تشغيل ومحاسبة بموافقتهم.
- جمع 200 مستند مصرح باستخدامه، إزالة بياناته الحساسة، وتحديد split ثابت للتطوير والاختبار.
- فصل فاتورة مورد `in_invoice` عن فاتورة عميل `out_invoice` قبل التوسع؛ المسار الحالي ينشئ مسودة مرتبطة بـ customerId ولا يمثل منظومة حسابات دائنين كاملة.
- قياس الزمن البشري اليدوي، زمن المراجعة مع وكيل، زمن الإصلاح، ونسبة الاستثناءات. لا استخدام fixtures التدريب كـ holdout.

### المقارنات المضبوطة

1. نفس النموذج ونفس الأدوات والبيانات: direct tool loop مقابل runtime.
2. نفس المهام وسياسة المخاطر: نموذج واحد مقابل توجيه نماذج، **بعد** توفر سجل tokens وفواتير مزود حقيقي.
3. تحقق مقابل عدم تحقق **في sandbox فقط**؛ لا تعطيل تحقق كتابة حقيقية لإجراء التجربة.
4. الاختبارات كلها تعرض failures/partials، لا إسقاط الحالات الصعبة من المقام.

### نموذج تكلفة قابل للقياس

```text
C_verified = (model + tools + compute + storage + orchestration
              + human_review + recovery + allocated_support) / verified_tasks

Net_value = measured_manual_baseline_cost - C_verified
```

- استبعاد انتظار الإنسان عند قياس latency الآلي، مع عرض زمن انتظار الموافقة منفصلًا.
- latency p50/p95، success-after-verification، retries، duplicate side effects، unauthorized writes، review burden.
- 0 أخطاء حرجة شرط اختبار إطلاق، وليس ضمانًا احتماليًا مطلقًا.
- إيقاف الإطلاق إذا محا وقت المراجعة/الإصلاح التوفير، أو تعذرت المصالحة، أو ظهر تسريب أو كتابة غير مصرح بها.

## 7. قبل أول عميل إنتاجي — موانع إطلاق

- Runtime منفصل مع queue وleases أو Temporal/Inngest، workers قابلة لإعادة التشغيل ومهل وحدود موارد وdead-letter queue.
- ربط الـ TaskStore بمصادقة خادمية وtenant derivation وRBAC، لا header يتحكم فيه الزائر.
- Odoo sandbox حقيقي، mapping كامل للمخرجات القياسية، unique external reference ومصالحة حقيقية.
- **مراجعة مسار Odoo القديم:** ما زال يخزن بيانات الاتصال في blueprint؛ يجب نقل الأسرار إلى vault وتدويرها ومنع ظهورها في responses/logs قبل استخدامه مع أسرار حقيقية.
- quotas وrate limits وretention وحذف بيانات ونسخ احتياطي واختبارات استرجاع.
- سجل تدقيق خارجي محمي من التعديل، وسياسة تنقيح تغطي النص الحر، وليس أسماء مفاتيح الأسرار فقط.
- CSP وframe-ancestors مناسبة للنشر الحقيقي؛ إعداد المعاينة يسمح بالـ iframe عمدًا.
- فصل environment للديمو عن الإنتاج وإغلاق `/api/demo/*` أمام بيانات العمل الحقيقية.
- اختبار حمل واقعي، SLO، alerting، اقتصاديات مقاسة، red-team على prompt injection والذاكرة قبل توصيل النموذج.

هذه ليست قائمة تجميلية: لا يُسوّق النظام كموظف «يعمل أي شيء» أو كطبقة تشغيل إنتاجية مستدامة قبل إغلاق تلك الحدود بالأدلة.
