# مواصفة WAKIL: الموظف المحاسبي الذكي

**الحالة:** مسودة للمراجعة قبل إعداد خطة التنفيذ
**تاريخ المراجعة:** 14 أكتوبر 2026
**المستودع المستهدف:** `shaker15s/wakeel`، استمرارًا للمشروع الحالي على `main`
**نقطة البداية التي فُحصت:** commit `0985a0f2e6c52784012aaee10ec2295b0dd20972`

هذه المواصفة تصف وجهة المنتج ومراحل بنائها فوق WAKIL الموجود. لا تعني أن كل المحاسبة ستُنجز في تعديل واحد، ولا تعتبر الادعاءات الموجودة في ملفات البحث أو الـprompt دليلًا على أن ميزة ما موجودة أو تعمل.

## 1. الهدف

تطوير WAKIL إلى موظف مالي ومحاسبي عربي/إنجليزي يفهم طلب صاحب العمل، يحوّله إلى خطوات محددة، ويستخدم أدوات الشركة المصرّح بها لقراءة البيانات وتحليلها وإعداد الأعمال المحاسبية. الـHarness والتطبيق هما المسؤولان عن الصلاحيات والسياسات والموافقات والتنفيذ والحفظ والتدقيق والتحقق. النموذج يقترح ويفسر؛ لا يمنح نفسه صلاحيات ولا يعلن نجاح عملية لم يتحقق النظام منها.

WAKIL طبقة تشغيل ذكية فوق ERP وأدوات الشركة القائمة، وليس دفتر أستاذ بديلًا أو نظامًا قانونيًا مستقلًا. يظل ERP المتصل مصدر الحقيقة للقيود والأرصدة والمعاملات. الواجهة شخصية، سريعة، ودودة ومختصرة، لكنها واضحة بشأن البيانات الناقصة والافتراضات والأخطاء.

## 2. ما يقدمه الموظف المحاسبي عند اكتمال نطاقه

تُضاف الوظائف كتخصصات مستقلة، كل منها بأدوات typed محددة وتقييم واختبارات وصلاحيات واضحة:

1. **دفتر الأستاذ والحسابات:** دليل الحسابات، الدفاتر، القيود، ميزان المراجعة، حركة الحساب، القيود المستحقة/المقدمة، وإقفال الفترات.
2. **الحسابات الدائنة:** الموردون، فواتير الموردين، إشعارات الخصم/الائتمان، تكرار الفاتورة، الاستحقاقات، وربط الفاتورة بأمر الشراء/الاستلام عندما تتطلب سياسة الشركة ذلك.
3. **الحسابات المدينة:** العملاء، الفواتير الصادرة، المقبوضات، الأرصدة المتأخرة، أعمار الديون، والإشعارات الدائنة.
4. **النقد والبنوك:** الأرصدة وكشوف البنك وحركة النقد ومطابقة البنود واقتراحات التسوية.
5. **المصروفات والأصول:** مصروفات الموظفين، المرفقات، تصنيف الأصل، سجل الأصول والإهلاك، وفق إعدادات الشركة وموافقتها.
6. **الضرائب والعملات:** عرض معدلات ومعالجات النظام المتصل ومصدرها وتاريخ سريانها؛ حسابات دقيقة حسب إعدادات العملة والـERP؛ التصعيد للمراجعة عند نقص الولاية الضريبية أو الإعداد أو المصدر.
7. **التقارير والتحليل:** قائمة الدخل، الميزانية، التدفق النقدي، تقارير AP/AR، مقارنة الفترات والميزانيات ومراكز التكلفة، مع إظهار المصدر والفترة والعملة وطريقة الحساب.
8. **المساعدة في التشغيل:** الإجابة على أسئلة صاحب العمل، طلب المعلومات الناقصة، اقتراح الخطوة التالية، وتجهيز ملخص/قائمة عمل مع أدلة قابلة للفحص.

كل وظيفة جديدة لا تُفتح لمجرد إضافتها إلى prompt؛ يجب أن يكون لها عقد بيانات، أداة مسجلة، صلاحية، سياسة، نتيجة موثقة، وقياس مستقل.

## 3. حدود الصلاحية والمحاسبة

- قراءات وتقارير ضمن صلاحيات المستخدم يمكن تنفيذها دون موافقة إضافية، مع مصدر البيانات والفترة والوقت.
- أي إنشاء أو تعديل أو حذف لسجل مالي، قيد يومية، تسوية أوامر دفع، تغيير مورد/عميل أو إعداد محاسبي يحتاج سياسة خادم وموافقة بشرية ملزمة ومربوطة بالمدخل المحدد والهدف والسياق والإصدار ومدة الصلاحية.
- الإصدار الأول لا يرسل مدفوعات، ولا يرحّل/يعتمد فواتير أو قيودًا، ولا يقدّم إقرارات ضريبية، ولا يغيّر الأرصدة الافتتاحية، ولا ينفذ حذفًا تدميريًا. يمكن تجهيز مسودات واضحة فقط حيث يدعمها ERP ويُختبر معناها.
- بعد الموافقة، يعيد النظام قراءة الحالة من المصدر ويتحقق من الحقول الجوهرية قبل عرض «تم». عند نتيجة كتابة مبهمة، يوقف إعادة المحاولة العمياء ويعرض «النتيجة غير محسومة—تلزم المطابقة اليدوية».
- لا تُستنتج دولة الشركة أو عملتها أو المعالجة الضريبية من لغة المحادثة أو مكان المستخدم. تُقرأ من إعدادات الشركة الموثقة أو تُسأل، وتظل مجهولة حتى التحقق.
- لا يُستخدم وصف مثل «لا يخطئ» أو «أدق من البشر» كمعيار قبول. المعيار هو الدقة المقاسة في حالات محددة، رفض التخمين، ووضوح أثر الخطأ وعدم اليقين.

## 4. الأساس الموجود في المستودع

المراجعة المحلية للنسخة الحالية وجدت تطبيق Next.js قائمًا، موصل Odoo، مسجل أدوات ERP قديمًا، مساعد محادثة، محرر/مساحة أنظمة، وسياسة وتنفيذ لمسار مسودة واحد، موصلًا تجريبيًا واختبارات تقييم. يجب إعادة تشغيل الفحوص بعد تجهيز dependencies قبل اعتبار أي نتيجة سابقة صالحة للحالة الحالية.

| الموجود في الكود | الحد الحالي الذي يجب الحفاظ عليه أو معالجته |
| --- | --- |
| `src/server/agent/runtime.ts` و`tools.ts` | مسار قديم يطلب قرار أداة بصيغة JSON ثم ينفّذها؛ ليس بعدُ حلقة أدوات موحدة ذات schema كامل ومتكاملة مع Task runtime. |
| `src/server/runtime/*` | حالة وموافقة وidempotency وتحقق لمسار `create_draft_invoice`، لكن `InMemoryTaskStore` ذاكرة عملية واحدة، وليس تخزينًا مستديمًا. |
| `src/server/erp/odoo-connector.ts` | تكامل Odoo عبر JSON-RPC، وواجهات canonical محدودة؛ يلزم التحقق من إصدار Odoo وخطة API وصلاحية كل عملية على النظام المستهدف. |
| `src/server/erp/contract.ts` | عقد ERP يتضمن ملخص المبيعات والذمم والمخزون وإنشاء مسودة فاتورة/أمر شراء، لكن وجود دالة في العقد لا يثبت اكتمال المسار أو سلامته. |
| `src/server/eval/scenarios.ts` | 16 حالة يدويّة لمسودة واحدة باستخدام fake connector؛ لا يوجد فيها مزود نموذج أو قاعدة بيانات حقيقية أو اختبار ضغط واقعي أو تحقق Odoo حي. |
| `prisma/schema.prisma` | Prisma/SQLite وجداول حسابات ومساحات ومحادثات، لكن لا توجد جداول Task/Step/Approval/Audit/Memory مالية متكاملة. |
| `src/lib/wakeel/ai.ts` | طبقة حالية لـOpenAI-compatible endpoint مع fallback إلى SDK آخر؛ تكتفي أساسًا بـJSON extraction/نص؛ تحتاج دراسة قبل إضافة native function calling أو تبديل المزود. |
| مستندات `docs/01..15-*` | عدة مواصفات مُدرجة في الشجرة فارغة حاليًا؛ تقارير التنفيذ موجودة لكنها تعود لـ4 أكتوبر وتصف نفس الحدود أعلاه. |

مسار الفاتورة القديم يستعمل `customerId` وموصفه يقول «customer invoice»، وبعض وثائق الـMVP تسميه «vendor bill». لا يجوز إعادة تفسير السجلات أو الـpayload بصمت. يُفصل نوع فاتورة العميل عن فاتورة المورد في العقود وأسماء workflows والاختبارات، وتُحافَظ على الدلالة القديمة أو تُرحّل بمراجعة صريحة.

المراجعة الأخيرة أعلاه تمت من الكود والملفات على commit المذكور؛ حالة git الأصلية نظيفة. clone الفحص محلي داخل `work/`، ولم يحدث تعديل أو commit أو push أو تغيير على GitHub.

## 5. معمارية الحل المقترحة

1. **واجهة WAKIL الحالية:** إضافة تجربة محاسبية داخل التطبيق، لا مشروع جديد. واجهة محادثة عربية RTL وإنجليزية LTR، سجل المهام، مصدر الأرقام، حالة التنفيذ، نموذج الموافقة، والإيصال النهائي. تُحترم هوية التصميم القائمة بعد معاينتها.
2. **سياق محادثة وهوية موثوقان:** المالك، الحساب، مساحة العمل، اتصال ERP، اللغة، الصلاحيات، وذاكرة العمل تُحل على الخادم. أي معرّفات/صلاحيات مرسلة من النموذج أو المتصفح لا تُعتبر هوية.
3. **طبقة التخطيط/الموديل:** نموذج واحد في الحلقة الأساسية لتقليل التعقيد؛ يختار بين أدوات قليلة وموثقة ذات مدخلات ومخرجات schema صارمة عندما يدعم المزود ذلك. لا ينفذ كودًا حرًا ولا SQL ولا shell ولا أدوات تلقائية غير مسجلة. الخادم يتحقق من كل استدعاء حتى لو التزم النموذج بالـschema. تُقاس جودة مزود آخر قبل تبديله.
4. **مسجل الأدوات المالية:** أدوات read/write صريحة مقسمة حسب المجال والصلاحية. الوصول إلى الأدوات حسب intent/capability لا يكشف كل سطح الأدوات دفعة واحدة. الاستعلامات العامة لا تقبل domain أو model عشوائيًا من النموذج.
5. **Harness تنفيذي:** Task/Step state machine مستمر، حدود وقت/عدد استدعاءات، إلغاء آمن، idempotency، استرداد بعد إعادة التشغيل، إعادة محاولة مصنفة، موافقات مرتبطة بالتصرف المحدد، سجل أحداث منقح، تحقق read-after-write، وإيصال يذكر ما طُلب وما قُرئ وما تغيّر وما لم يُحسم.
6. **الذاكرة:** فصل ذاكرة المحادثة عن إعدادات الشركة. تحفظ تفضيلات مثل طريقة عرض الملخص أو اسم مركز تكلفة بعد تأكيدها، مع النطاق والمصدر والتاريخ والثقة وإمكانية العرض/التعديل/الحذف. قواعد المحاسبة/السياسة لا تُستنتج تلقائيًا من دردشة ولا تصبح إذنًا؛ يلزم إعداد موثق وموافقة مخول.
7. **قاعدة البيانات:** البناء فوق Prisma/SQLite الموجود أولًا وتحديد migrations آمنة. لا تبديل تلقائيًا إلى Supabase أو قاعدة أخرى لأن أسماء plugins ذُكرت؛ إذا كان التشغيل متعدد النسخ أو النشر يتطلب PostgreSQL، يُسجّل قرار منفصل ويدعم انتقالًا آمنًا بعد تحديد بيئة النشر.
8. **موصل النظام:** Odoo أولًا عبر العقد القائم بعد مطابقة API المتاحة للنسخة والخطة والصلاحية والسجلات. كل Connector يكشف capabilities مؤكدة لكل عملية. تبقى FakeERP للاختبارات؛ لا توصل بيئة حيّة ضمن هذا العمل بلا تصريح منفصل واختبار sandbox.
9. **التقارير:** الحسابات الحتمية وتجميع الأرصدة تتم في الكود/ERP باستخدام مبالغ عشرية وrounding/precision الخاصة بالعملة وإعدادات النظام؛ النموذج يشرح النتيجة ولا يجمع بيانات مالية على نحو غير قابل لإعادة الحساب.

## 6. مراحل التنفيذ المقترحة

**المرحلة 0 — خط أساس حالي:** تثبيت branch عمل على GitHub بعد اعتماد الخطة، حفظ أي تغييرات موجودة، إعادة قراءة تعليمات المستودع، تشغيل تثبيت وفحوص المشروع، إعادة إنتاج التقارير، وتحديث audit بالمخاطر والفجوات الحالية. لا كتابة إلى ERP حي.

**المرحلة 1 — الموظف/Harness والذاكرة المستديمة:** دمج المحادثة مع tool registry وruntime بدل المسارين المنفصلين؛ حفظ الرسائل/المهام/الأحداث/الموافقات في DB المعتمدة؛ هوية ومساحة عمل server-derived؛ ذاكرة قابلة للعرض والإدارة؛ receipts؛ حدود الأدوات والسياسات واختبارات injection. هذه قاعدة إلزامية قبل التوسع في العمليات.

**المرحلة 2 — أساس المحاسبة للقراءة والتحليل:** أدوات آمنة ومحدودة لاستكشاف شجرة الحسابات والدفاتر والفترات والعملة، حركة حساب، ميزان مراجعة، AP/AR aging، وقوائم/ملخصات مشتقة من بيانات ERP. مصادر كل رقم وتاريخه وعملته واضحة. اختبار multistep مع أسئلة متابعة وتغيّر الفترة.

**المرحلة 3 — دورة AP/AR للمسودات:** فصل مسودة فاتورة مورد عن مسودة فاتورة عميل، إدخال/استخراج البيانات من النص أو الإدخال المنظم، فحص الحسابات والتكرار والمورد/العميل والضريبة المهيأة، ثم موافقة دقيقة وإنشاء مسودة والتحقق منها في FakeERP أولًا. Odoo sandbox مرحلة تحقق اختيارية منفصلة.

**المرحلة 4 — قيود ومطابقة ومصروفات:** إعداد مسودات القيود، اقتراح مطابقة البنك والوثائق، ومصروفات/أصول ضمن سياسة واضحة؛ كل عملية كتابة موافَق عليها ومتحقق منها.

**المرحلة 5 — إدارة مالية موسعة:** موازنات ومراكز تكلفة وإقفالات دورية وتسويات ومراجعات وإحصائيات محسوبة من بيانات فعلية. كل نطاق يتطلب معايير قبول واختبارات منفصلة وتكوينات متحققة.

**المرحلة 6 — تكامل ومراجعة إطلاق:** موصلات إضافية فقط بحسب الأنظمة المطلوبة، اختبار صلاحيات/tenant boundaries وrestart وreconciliation، مراجعة وصول شامل، سجل مخاطر وrunbook. لا ادعاء جاهزية إنتاج إلا بعد تجربة ميدانية مصرّح بها ونتائج موثقة.

المقترح أن تبدأ خطة التنفيذ بالمرحلة 0 ثم المرحلة 1 و2 لتكون هناك منظومة موظف حقيقية ومستمرة وآمنة قبل توسيع أنواع المعاملات. تُنفذ كل مرحلة على branch مراجعة وبـPR؛ لا merge أو deploy أو تنفيذ معاملات حقيقية تلقائيًا.

## 7. اختبارات القبول والتجربة المطلوبة

### شروط عامة

- مهمة متصلة عبر عدة رسائل تستعيد ملخص السياق الصحيح، وتفصل fact عن assumption، ولا تستدعي أداة إلا عند الحاجة.
- سؤال عن رصيد/تقرير يذكر النظام والفترة وتاريخ القراءة والعملة وأساس التجميع؛ لا يخترع رقمًا عند تعذر ERP.
- حساب الإجمالي والضريبة/الخصم/الكمية يتطابق مع oracle عشري deterministic وتكوين الشركة؛ قيم غير مدعومة أو عملة/ولاية مجهولة ترفع `REVIEW_REQUIRED`.
- التكرار أو بيانات المورد الخاطئة أو مستند مقتبس يحتوي تعليمات لـ«تجاوز الموافقة/كشف الأسرار» لا يغير الصلاحيات ولا يسبب كتابة.
- رفض الموافقة أو انتهاء صلاحيتها أو تعديل مبلغ/طرف/سطر بعد الموافقة يمنع التنفيذ.
- طلب عملية غير مسجلة، محاولة عبور tenant، أو إعادة تشغيل طلب بنفس idempotency key وpayload مختلف تُرفض.
- timeout بعد side effect لا ينشئ فاتورة ثانية ولا يظهر نجاحًا غير متحقق.
- الذاكرة تتذكر تفضيلًا مصرحًا به عبر جلسة لاحقة ضمن الحساب/الشركة فقط، وتحدّث/تنسى القيمة عند الطلب، ولا تحفظ سرًا أو قاعدة ضريبية كحقيقة معتمدة.
- المنتج يتعامل مع العربية والأرقام/العملة/المراجع المعزولة بصريًا ويدعم لوحة المفاتيح وحالات الخطأ.

### اختبار المستخدم بصاحب شركة

ينفذ تقييم تفاعلي versioned فيه حالات متنوعة فعلية وليست نسخًا مكررة: (أ) يهيئ عملة وتفضيل عرض ويطلب حفظه، (ب) يطلب ملخص المصروفات ثم يسأل أسئلة متابعة لا تكرر الطلب، (ج) يرفع/يلصق مستند مورد له مجموع غير مطابق فيكتشف الفارق ويسأل عن المعلومة الناقصة، (د) يغير قاعدة تصنيف بعد تصحيح المساعد ثم يختبر الذاكرة، (هـ) يقدم مستندًا مكررًا، (و) يحاول تمرير تعليمات غير موثوقة داخل المستند، (ز) يراجع مسودة وموافقتها ثم يرفضها/يعدلها، (ح) يطلب تقريرًا لفترة أخرى وعملة أخرى، (ط) يختبر عدم خلط معلومات شركتين/مستخدمين.

تُقيّم السيناريوهات ببيانات صناعية ثابتة وexpected outputs وحالة ERP قابلة للفحص. تُفصل نتائج الاختبارات الحتمية، محاكي ERP، بيئة Odoo sandbox، ومزود النموذج الحي إن فُوض استخدامها. لا تستنتج «الدقة العامة» أو «أسرع من البشر» من حجم صغير؛ اعرض العدد والفشل وتفسيره وكلفة/زمن التشغيل عند القياس فقط.

## 8. معايير إتمام أول مراحل البناء

1. محادثة WAKIL الحالية تستخدم حلقة أدوات منظّمة مرتبطة بالـruntime، والـtools غير المعروفة مرفوضة.
2. الرسائل والمهام والموافقات والأحداث/الذاكرة المطلوبة باقية بعد restart في قاعدة التطبيق، وتُختبر باستخدامها فعلًا.
3. مستخدم لا يستطيع قراءة أو تنفيذ مهمة أو ذاكرة tenant آخر؛ التحقق يتم على الخادم.
4. كل output مالي حتمي قابل لإعادة الحساب وله evidence، والتباس العملة/الضريبة/نوع المستند لا يُخمّن.
5. عمليات الكتابة تتوقف عند الموافقة المطلوبة؛ لا تملك الخدمة مسارًا يقفز عن السياسة أو التحقق.
6. فصل semantics للمورد والعميل ظاهر في واجهة المستخدم وAPI وعقد Odoo والاختبارات.
7. تقييم business-owner متعدد الرسائل يتضمن حسابات وذاكرة وتعارضات ورفض وتلاعب واسترداد، مع تقرير versioned.
8. فحوص typecheck/lint/build/tests الموجودة تجتاز أو تُوثق فروق الأساس بدقة؛ لا تعد واجهة demo أو fake دليل تشغيل إنتاجي.

## 9. ما لا تقرره هذه المواصفة

الدولة/الضرائب المستهدفة، الحساب البنكي أو نظام الدفع، Odoo version/plan/API المتاح، مزود/اسم/كلفة النموذج، قاعدة بيانات الإنتاج، مكان الاستضافة، سياسة حفظ المستندات، ضوابط اعتماد القيود، ومستخدمو الموافقة. تُضبط من إعدادات المستودع/بيئة اختبار أو طلبات لاحقة؛ إن غابت، يبقى المسار المحاسبي المتأثر مقروءًا أو في المراجعة ولا يكتب.
