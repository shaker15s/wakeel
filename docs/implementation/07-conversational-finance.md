# من مختبر فاتورة إلى موظف مالي محادثي

14 أكتوبر 2026 · `arena/94e3a7c0-wakeel`

المرجع الأساسي: `تحويل الذكاء الاصطناعي من وكيل إلى موظف رقمي_ تقرير فحص جدوى WAKIL كطبقة تشغيل مستدامة (1).md`.

## تصحيح جوهري للمنتج

اختزال WAKIL في شريحة إنشاء فاتورة لم يحقق طلب المستخدم. الشريحة السابقة مفيدة لاختبارات موثوقية محددة، لكنها ليست تجربة الموظف المطلوب. نُقلت إلى `/lab`؛ الصفحة الرئيسية الآن ترحيب وإدخال طبيعي يبدأ جلسة جديدة. لا نموذج فاتورة ولا خطة ثابتة مخفية تحت دردشة.

الدورة الحالية:

1. حفظ طلب المستخدم بهوية جلسة ومساحة مستقلة.
2. استرجاع مستندات وسياسات ذات صلة؛ تمرير فهرس المصادر للنموذج.
3. طلب خطة فعلية من نموذج OpenAI-compatible، والتحقق من أدواتها وتبعياتها وحدودها.
4. تنفيذ أدوات الذاكرة وقراءة ERP والحسابات، وحفظ نتائج كل خطوة.
5. عرض النشاط الحقيقي، لا سلسلة التفكير الداخلية ولا progress مصطنع.
6. إنتاج إجابة مدعومة بالمخرجات. إن كانت هناك كتابة، إنشاء مقترح منفصل للمراجعة البشرية، لا اعتباره فعلًا منفذًا.

لا مفاتيح نموذج أو Odoo متاحة هنا، وشبكة بيئة المعاينة مقيّدة. لذلك لم يُختبر الربط الحي، والجلسة غير المهيأة تتوقف بوضوح بدل رد اصطناعي مُعد مسبقًا.

## الفصل المعماري

| المكوّن | المسؤولية |
|---|---|
| `types.ts` | عقد الأدوات والخطة والحالة والموافقة، DAG مرتب، قيد متوازن ودقة ومواعيد صحيحة |
| `store.ts` | SQLite، مساحة ذات capability عشوائية، مصادر ببصمات، جلسات، خزنة AES-GCM |
| `transport.ts` | HTTPS عام فقط، DNS مثبت للسوكيت، لا redirects، حدود اتصال واستجابة |
| `model.ts` | تخطيط فعلي ثم صياغة مبنية على الأدلة، تعامل مع المستندات كبيانات غير موثوقة |
| `calculations.ts` | حساب مستقل عن النموذج، CSV صارم، أعمار مديونيات، فصل العملات وتجميع الصفوف |
| `odoo.ts` | قراءات محددة لشركة واحدة، عدد شامل/نتائج مقيدة، تحضير قيد وكتابة واحدة وتحقق |
| `runner.ts` | تنفيذ وحفظ وعرض مراحل، تبعيات صريحة، استئناف النتائج المكتملة، بوابة اعتماد |
| API | مساحة موثقة بالـ bearer، body/rate limits، إعدادات ومصادر وNDJSON |
| React workspace | ترحيب وجلسات ومصادر، نشاط، مراجعة أدلة، ذاكرة، اتصالات، اعتماد، RTL وموبايل |

تلك خدمة جديدة منفصلة عن الوكيل القديم ذي الأداة الواحدة. لم يُعَد استخدام fallback النجاح الوهمي أو التخزين القديم للأسرار.

## أدوات مالية متعددة وليست workflow فاتورة

- `memory.search` / `memory.read`: استرجاع أو قراءة مصدر بعينه في نفس المساحة.
- `finance.table_summary`: جمع من ملف CSV محفوظ مباشرة، وليس أرقامًا أعاد النموذج نسخها. التحقق من الاقتباسات والصفوف والأعمدة؛ لا تقطيع صامت.
- `finance.calculate`: decimal cents بـ BigInt، وhalf-away-from-zero عند التقريب اللازم، ورفض الدقة الزائدة أو القسمة على صفر.
- `finance.aggregate`: تجميع القيم الأصلية من صفوف القراءة. فصل العملات والمجموعات. منع التعامل مع debit/credit/balance بوصفها عملة المعاملة بدل الشركة.
- `finance.ageing`: توزيع مبالغ على فترات تأخر، حسب العملة، وإظهار التواريخ المفقودة.
- `odoo.read`: سبعة أنواع بيانات مالية، domain ثابت وآمن للشركة، تواريخ اختيارية، حد 200 سجل، وعلامة نقص التغطية.
- `odoo.propose_journal`: تحقق من الدفتر والحسابات ثم اقتراح مسودة قيد، دون كتابة وقت التخطيط.

لا دفع أو ترحيل أو حذف أو تنفيذ Python/SQL أو أداة shell من النموذج. الطلب غير المدعوم يظهر كقيد أو سؤال، لا يُستبدل ضمنيًا بإنشاء فاتورة.

## ضمانات محدودة قابلة للاختبار

### الخطة والأدلة

حتى 10 خطوات، IDs فريدة وتبعيات سابقة فقط. مراجع مثل `{{read.rows}}` لا تصل إلا إلى مخرج خطوة مكتملة مُعلنة في dependencies، مع حظر خصائص prototype. لا إعادة تنفيذ خطوة مكتملة عند فشل صياغة التقرير. تغيير اتصال Odoo بعد قراءة بيانات يوقف الاستئناف بدل خلط شركتين. لا تقطيع صامت للأدلة لتجاوز ميزانية التقرير.

### أرقام لا تُجمع عشوائيًا

فصل العملة إلزامي في التجميع. نطاق AR الحالي هو فواتير العملاء المفتوحة، وليس صافي الذمم بعد أرصدة دائنة ومدفوعات غير مخصصة؛ يخرج هذا التحفظ مع البيانات. القيود المرحلة ليست تقريرًا نظاميًا جاهزًا، ومبالغ الفواتير ليست إيرادًا معترفًا به تلقائيًا. حد منزلتين معلن، وليس ادعاء دعم جميع العملات.

### الموافقة والأثر الخارجي

بصمة الموافقة تربط **الإجراء نفسه + إعدادات الاتصال**، وصلاحيتها 24 ساعة. تُحفظ `executing` قبل استدعاء create واحد. بعده يلزم قراءة نفس القيد ومطابقة الحالة draft والمرجع والتاريخ والدفتر والبنود والمبالغ.

أي مهلة أو نتيجة ملتبسة بعد بدء الكتابة تتحول إلى `unknown`، بلا retry تلقائي. بعد موت العملية تتحول الموافقة العالقة executing إلى unknown للمراجعة بالمرجع WAKIL. لا ضمان exactly-once، ولا مصالحة آلية، ولا نجاح مبني على مجرد HTTP 200. القفل داخل العملية؛ تشغيل عدة workers غير مدعوم.

### الذاكرة والخصوصية

المصادر يضيفها المستخدم صراحة؛ يمكن مراجعتها وحذفها. لا embeddings، ولا تعلم خفي، ولا سياسة تمنح نفسها سلطة كتابة. `workspace token` ليس هوية مؤسسية. المفاتيح مشفرة؛ النصوص المالية والأدلة في SQLite ليست مشفرة. البيانات ذات الصلة ونتائج الأدوات تصل للمزوّد عند التخطيط والتقرير؛ لا ترفع بيانات حساسة لهذه النسخة المحلية.

## الاستعادة والحدود الصريحة

SQLite مع WAL وFULL synchronous، وحفظ بعد كل انتقال/مخرج. إعادة الفتح تسترجع الحالة؛ جلسة running بلا تنفيذ داخل العملية تظهر interrupted. الاستئناف يدوي. بعد تحديث المتصفح أثناء تشغيل قائم، polling للحالة يكمل المتابعة؛ ليس تنفيذًا وهميًا في المتصفح.

هذا **ليس durable worker orchestration** بالمعنى الكامل في البحث. التنفيذ ما زال داخل طلب HTTP بمهلة 170 ثانية، والطلبات الخارجية bounded. لا queue أو lease أو scheduler أو موافقات ذات هوية قانونية. لا يصح استخدامه لتشغيل مالي إنتاجي طويل الأجل قبل نقل التنفيذ لعامل مستقل وإغلاق هذه الفجوات.

## تجربة المنتج

الصفحة الأولى تشبه مدخل محادثة هادئ، لا لوحة مؤشرات محشوة. أمثلة التحصيل والمصروفات ومراجعة القيود تبدأ طلبًا كاملًا. تفاصيل الأدوات والأحداث والمخرجات تظهر عند الحاجة. زر جديد، سجل بحث، إرفاق، لوحة مصادر، إعدادات، إشعارات، تصدير، اختصار Ctrl/⌘+K، وحركة صغيرة في الشعار. تحترم الحركة prefers-reduced-motion. لا رسوم تكاملات مزيفة أو عدادات نجاح وهمية.

## التحقق والتفسير الصحيح للنتائج

التحقق المحلي يشمل الاختبارات في `tests/finance` و`tests/browser/finance.spec.ts`، بالإضافة إلى عدم كسر مختبر الموثوقية السابق. اختبارات التخطيط والتقرير وOdoo تستخدم بدائل حقن مخصصة للاختبار؛ تثبت عقود التنفيذ والحساب والحماية، **ولا تثبت دقة مزوّد حي أو توافق شركة Odoo فعلية**.

رحلة المتصفح تختبر التطبيق الحقيقي وقاعدة بياناته: ترحيب، جلسة بطلب حر، توقف صريح لعدم الاتصال، استعادة، مكتبة وسياسة، إرفاق، عزل bearer، شاشة إعدادات، موبايل، وفحوص axe. نتائج الإصدار النهائية تُذكر بعد تشغيل lint/typecheck/Vitest/build/Playwright، لا تُستعار من نجاحات المختبر القديم.

## ما يلي قبل عميل حقيقي

1. بيئة شبكة مسموحة، مزود نموذج محدد، Odoo sandbox، fixtures محاسبية مع نتائج متوقعة، واختبارات read/approval/readback بحساب محدود.
2. مصادقة وخادم صلاحيات، فصل واضع الطلب عن معتمده، إبطال tokens، وعدم الاعتماد على localStorage بوصفه هوية موظف.
3. worker/queue وleases وفencing، تزامن متعدد العمليات، native idempotency أو مصالحة معرّفة لكل أثر خارجي.
4. تشفير المستندات، KMS ودوران الأسرار، سجل append-only محمي، retention ونسخ احتياطي واستعادة واختبارات فقد القرص.
5. استخراج PDF/Excel/OCR بإسناد للصفحات والخلايا، بحث معرفي مضبوط، صلاحيات المصدر، واختبارات prompt injection واقعية.
6. تقييم استنتاجات النموذج واستشهاداته، تعامل صحيح مع أرصدة دائنة وقطع الفترات والعملات، وقياس الخطأ المالي لا صحة النص فقط.
7. اقتصاديات تنفيذ حقيقية: tokens + الأدوات + retries + المراجعة البشرية + الدعم. تصحيح وحدات البحث محفوظ: $0.00791 = 0.791 سنت، و$0.06374 = 6.374 سنت. لا ROI أو SLA مُختلق قبل قياسات فعلية.

الغرض من هذه المرحلة: تحقيق شكل العمل الصحيح وبناء عمود تنفيذي متعدد الأدوات، لا إعلان اكتمال كامل خارطة البحث أو استبدال المحاسب دون إشراف.

## نتيجة التحقق المحلي لهذه المرحلة

على النسخة النهائية، 14 أكتوبر 2026:

- Vitest: **132 اختبارًا ناجحًا** في 16 ملفًا، منها **40 اختبارًا للمحرك المالي الجديد**.
- `npm run build`: بناء الإنتاج ناجح.

- أُنشئت جلسة بطلب حقيقي غير مهيأ للاتصال، ثم أُوقفت عملية الإنتاج وأُعيد تشغيلها: استُعيد نفس الطلب وحالة blocked باستخدام نفس مفتاح المساحة.
- مراجعة بصرية لسطح المكتب والموبايل، وعدم overflow على عرض 390px.
- لا اختبار حي لمزوّد نموذج أو Odoo، ولا ادعاء CI بعيد أو اعتماد إنتاجي.
